# 커밋 컨벤션

커밋 메시지는 staged diff가 실제로 수행한 가장 중요한 변경 하나를 설명한다.

## 형식

```text
<emoji> <type>(<scope>): <한글 요약>
```

- `type`은 소문자로 작성한다.
- `scope`는 선택 사항이며 모듈·도메인·도구 이름을 소문자 kebab-case로 작성한다.
- 요약은 변경 결과를 간단한 한글 명사형으로 작성하고 마침표를 붙이지 않는다.
- 서로 다른 목적의 변경은 커밋을 나눈다.
- AI 공동 작성자 트레일러는 사용하지 않는다.

## 유형

| 접두어 | 용도 |
|---|---|
| `✨ feat` | 새로운 기능 |
| `🛠️ fix` | 버그 수정 |
| `🏢 build` | 빌드 설정, 의존성·모듈 추가 또는 삭제 |
| `🔨 chore` | 그 외 자잘한 유지보수 |
| `👷 ci` | CI/CD 설정 |
| `📄 docs` | 문서 변경 |
| `💄 style` | 동작 변화 없는 코드 포맷·스타일 변경 |
| `♻️ refactor` | 기능 변화 없는 구조·컨벤션 개선 |
| `✅ test` | 테스트 추가·수정 |
| `⚡ perf` | 성능 개선 |
| `⚙️ config` | 애플리케이션 설정 변경 |
| `💾 db` | 스키마·마이그레이션 변경 |
| `🔥 remove` | 코드·파일 제거 |

`💻`, `🎨 design`, `🍺 beer`, `💩 boob`, `📦 package`는 의미가 불명확하거나 기존 유형과 중복되므로 사용하지 않는다.

## 선택 기준

1. 사용자 기능이 추가되면 `feat`, 잘못된 동작을 고치면 `fix`를 사용한다.
2. 기능은 같고 내부 구조만 바뀌면 `refactor`, 실행 성능이 목적이면 `perf`를 사용한다.
3. 의존성·Gradle·모듈 구조는 `build`, 런타임 설정은 `config`, 자동화 파이프라인은 `ci`를 사용한다.
4. 코드와 테스트가 함께 바뀌면 코드 변경의 목적을 따른다. 테스트만 바뀌면 `test`를 사용한다.
5. 여러 유형이 섞이면 가장 중요한 목적을 선택하거나 커밋을 나눈다.

## 예시

```text
✨ feat(ai): Stop 훅 기반 자동 교정 루프 구현
🛠️ fix(data): 삭제 대상 미존재 처리 수정
📄 docs(ai): 커밋 메시지 규칙 추가
♻️ refactor(credit): 결제 검증 책임 분리
🔥 remove(data): 미사용 레거시 어댑터 제거
```

Git이 생성하는 `Merge`, `Revert`, `fixup!`, `squash!` 메시지는 예외로 허용한다.
